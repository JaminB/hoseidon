# Deploying to Cloudflare Workers (Free plan)

CI deploys Hoseidon to Cloudflare Workers on every push to `main` after the checks pass. Until the
two Cloudflare secrets below exist, the `deploy` job is skipped (shows a notice, stays green).
Design background: [cloudflare.md](cloudflare.md).

Everything here works on the Free plan. Do not enable Workers Paid.

## 1. Create the API token

1. Cloudflare dashboard > My Profile > API Tokens > Create Token.
2. Use the template **Edit Cloudflare Workers**.
3. Account Resources: Include > your account only (account-scoped). Zone Resources: you can leave
   "All zones" or restrict it; workers.dev needs no zone.
4. Create, then copy the token (shown once).

## 2. Find the account ID

Dashboard > Workers & Routes: the Account ID is on the right. It is also in the dashboard URL
(`dash.cloudflare.com/<account id>/...`). Also, once, open Workers & Routes and register your
`workers.dev` subdomain if it asks.

## 3. Set the GitHub secrets

Create the Environment once (Settings > Environments > New environment > `production`; optionally
add required reviewers). Then, from the repo:

```sh
gh secret set CLOUDFLARE_API_TOKEN  --env production
gh secret set CLOUDFLARE_ACCOUNT_ID --env production

# Generated, never reused elsewhere:
openssl rand -base64 18 | gh secret set ADMIN_PASSWORD  --env production   # 20+ chars required
openssl rand -hex 32    | gh secret set SESSION_SECRET  --env production
openssl rand -hex 16    | gh secret set WEBHOOK_SECRET  --env production

# Google sign-in and Calendar (section 6):
gh secret set GOOGLE_CLIENT_ID --env production
gh secret set GOOGLE_CLIENT_SECRET --env production
gh secret set ADMIN_EMAIL --env production   # your Google account's address; comma-separated for more

# Only when switching to real taps (see section 7):
gh secret set LINKTAP_USERNAME --env production
gh secret set LINKTAP_API_KEY  --env production
```

With GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET and ADMIN_EMAIL all set, Hoseidon uses **Sign in with
Google** and password sign-in is off (ADMIN_PASSWORD is ignored and no longer required). Without
them it keeps the ADMIN_PASSWORD login. With real taps, one of the two must be set up.

Only non-empty secrets are pushed (`wrangler secret bulk`), so an unset one never blanks a value
already stored in Cloudflare. Each push makes a new Worker version (restarting the Durable Object),
so an ordinary merge pushes only secrets Cloudflare does not have yet. To rotate one, update the
GitHub secret and run the CI workflow manually on main with `push_secrets` ticked. Docs-only
merges skip CI/deploy, and the `production` environment only accepts deploys from `main`. Write down ADMIN_PASSWORD and WEBHOOK_SECRET: you need them to log in
and to register the webhook. VAPID push keys are generated by the app and stored in its database;
there is nothing to set.

Optional variables (Settings > Variables, or `gh variable set NAME --env production`), each
overriding `apps/worker/wrangler.jsonc` when set:

| Variable                | Meaning                                                             |
| ----------------------- | ------------------------------------------------------------------- |
| `LINKTAP_MOCK`          | `true` (default) uses the fake LinkTap; `false` = real taps         |
| `ENGINE_ENABLED`        | must be `true` for the scheduler to run with real taps              |
| `PUBLIC_URL`            | custom domain; otherwise the first request's origin is adopted      |
| `TZ`                    | IANA time zone for schedules                                        |
| `CLOUDFLARE_WORKER_URL` | `https://hoseidon.<subdomain>.workers.dev`, used by the smoke check |

## 4. First deploy

Merge to `main` (or re-run the CI workflow on main). The `deploy` job builds the web app, runs
`wrangler deploy` (creating the Worker, the `Brain` Durable Object and the cron trigger), pushes
secrets, then curls `/api/health` up to 10 times. The URL is printed in the log
(`https://hoseidon.<subdomain>.workers.dev`); set it as `CLOUDFLARE_WORKER_URL` to make the smoke
check independent of log parsing. Open it and sign in: with Google (as an ADMIN_EMAIL account)
when it is configured, otherwise with ADMIN_PASSWORD.

You can also deploy by hand: `CLOUDFLARE_API_TOKEN=... corepack pnpm build &&
corepack pnpm --filter @hoseidon/worker exec wrangler deploy`.

## 5. Register the LinkTap webhook

In the LinkTap portal, set the webhook URL to:

```
https://<worker>.workers.dev/hooks/linktap/<WEBHOOK_SECRET>
```

The secret is in the path, which is why invocation logs are disabled in `wrangler.jsonc`.

## 6. Google sign-in and Google Calendar

One OAuth client serves both. In Google Cloud Console > APIs & Services:

1. OAuth consent screen: app name, your email as support contact, scopes `openid`, `email`,
   `profile` (sign-in) and `calendar.app.created` (Calendar, optional). While the app is in
   **Testing**, add every Google account that should sign in as a test user (or publish it).
2. Credentials > Create credentials > OAuth client ID > Web application. Authorised redirect
   URIs (both, exactly):
   - `https://<worker>.workers.dev/api/auth/google/callback` (sign-in)
   - `https://<worker>.workers.dev/api/gcal/callback` (Calendar)
3. Set the GitHub secrets GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET and ADMIN_EMAIL (your own
   Google account's address) and re-run the deploy (manually with `push_secrets` if Cloudflare
   already has some of them).

Then sign in with Google. ADMIN_EMAIL accounts are always admins: they can't be removed or demoted
from the app. An admin invites others by email (member or admin); only invited addresses can
sign in, everyone else sees a "not invited" message and gets no session. Removing or disabling
someone signs them out everywhere and deletes their passkeys. Turning Google sign-in on ends the
old password session and retires passkeys registered with it: sign in with Google and add a
passkey again.

If you later move to a custom domain, set `PUBLIC_URL` and update both redirect URIs. Passkeys
are bound to the hostname: register them again after any hostname change.

## 7. Going live with real taps

Keep `LINKTAP_MOCK=true` until the budget work in docs/cloudflare.md (phase D) is done. Then set
`LINKTAP_MOCK=false` and `ENGINE_ENABLED=true` variables, set the LinkTap secrets, and re-run the
deploy. With real taps and weak secrets, every `/api` route, health included, answers 503 (so the deploy smoke check fails instead of
passing on a refusing app), and so does a live deployment with no LinkTap credentials yet.

## Staying inside the Free plan

Limits that matter (details and measurements in docs/cloudflare.md): 100,000 Worker requests per
day, 100,000 Durable Object requests per day, 100,000 rows written and 5M rows read per day, 13,000
GB-s per day, 10 ms CPU per request, 5 cron triggers. Static assets are free and unlimited.

Expected household use is about 8.5k Worker requests and 11.5k DO requests per day. Habits that
keep it that way:

- One Durable Object only (never add a second); one cron (every 10 minutes).
- Do not leave many browser tabs polling; do not add more scheduled triggers.
- Keep Workers Logs at its default sampling; do not add Logpush or other paid features.

If a limit is hit, Cloudflare does not bill you on the Free plan: requests that exceed the daily
Worker or DO quota fail (HTTP 1015/5xx style errors) until the counters reset at 00:00 UTC. The
effect is that the UI and webhook stop answering and the Durable Object alarm may not run, so
**scheduled waterings can be missed** until the reset. Valves already running are stopped by the
LinkTap device's own run time. If this ever happens regularly, check the Workers dashboard usage
graph and reduce polling; the supported fallback is the Node/Docker target (README).
